# pPhone.home — концепция

Домашняя/офисная VoIP-система на Asterisk с кастомным веб-телефоном и
фоновым ботом, который автоматически заходит в каждый звонок как
третий участник, слушает его и в реальном времени выводит
транскрипцию на экран веб-клиента — прямо в окне звонка.

Любой звонок = **3 стороны**: абонент A, абонент B, бот-слушатель.

## Ключевое архитектурное решение: бот — обычный SIP UA, не Asterisk-ARI-хак

Нет гарантии, что у клиента в проде будет именно Asterisk (может быть
другой PBX/облачная АТС). Поэтому бот реализован как **обычный SIP
участник конференции**, а не через Asterisk-специфичные ARI-механизмы
(Snoop channel / ExternalMedia). Конференц-звонок (3-way call) — почти
универсальная фича любого SIP PBX (Asterisk ConfBridge/MeetMe,
FreeSWITCH mod_conference, 3CX, большинство cloud-АТС), поэтому сам бот
не меняется между платформами — отличается только dialplan-обвязка под
конкретный PBX.

**Следствие для диаризации**: будучи обычным конференц-участником, бот
физически получает **один смикшированный аудио-поток** (как слышал бы
третий собеседник по телефону), а не раздельные потоки по сторонам.
Поэтому:
- Фаза 1 (демо) — единый транскрипт без разметки «кто говорит».
- Фаза 2 — настоящая диаризация смикшированного потока (детекция смены
  говорящего / speaker embeddings, например pyannote).

## Контейнеры

### 1. `asterisk` — ядро телефонии
- `pjsip.conf`: 3 SIP/WebRTC-аккаунта — абонент A, абонент B, `bot`.
- `confbridge.conf` + `extensions.conf`: любой звонок между A и B
  физически заводится как `ConfBridge`-комната с тремя участниками
  (A, B и уже присутствующий там `bot`).
- Для production-сценария (бот подключается на *любой* звонок, а не
  только в статическую демо-комнату) понадобится динамическое создание
  комнаты на каждый звонок — вне рамок простого демо.
- Том с конфигами + (опционально) записями разговоров.

### 2. `webclient` — кастомный веб-телефон (user-facing)
- Базовая SIP/WebRTC-библиотека (JsSIP или SIP.js) + свой фронтенд
  (React/Vue), который будем переделывать под «специальный интерфейс».
  На старте разумно взять минимальный open-source webphone (JsSIP demo)
  как скелет, а не тяжёлый готовый продукт (FreePBX UCP/Wazo) — их
  сложнее кастомизировать под нестандартный UI.
- Два подключения:
  1. **SIP over WSS** → `asterisk` (регистрация, звонки, медиа);
  2. **WebSocket** → `transcriber` (получение текста в реальном времени
     по `room_id` текущего звонка).
- UI: окно звонка + «живые субтитры» прямо в нём (не отдельное окно),
  история звонка.

### 3. `transcriber` — фоновый бот-слушатель
- Обычный SIP UA, который сам регистрируется на PBX и автоматически
  заходит в конференц-комнату звонка (для демо — в одну статическую
  `demo_room`). Рекомендуемая база для SIP/RTP-стека — **pjsua2**
  (Python-биндинги PJSIP): даёт прямой программный доступ к
  декодированным аудио-фреймам звонка без написания SIP/RTP с нуля.
- Принимает RTP → декодирует в PCM → подаёт в STT-движок.
- **STT-движок (решено)**: сервер — 4 ядра i5-6500T, 16GB RAM, без GPU
  (только Intel iGPU, не CUDA). Внешний облачный STT не требуется —
  локально на CPU поднимаем **faster-whisper** (`base`, int8-квантование
  через CTranslate2): укладывается в реалтайм на одном аудиопотоке,
  модель ~140MB, память/диск — не проблема на этом железе. Чанки
  2–5 сек с перекрытием (Whisper не потоковый по природе, это даёт
  задержку в несколько секунд на партиалах — для демо приемлемо).
  Если в проде понадобится минимальная задержка в ущерб точности —
  запасной вариант **Vosk** (ru-small) — truly streaming, легче CPU,
  но хуже с пунктуацией.

  **STT как подключаемый адаптер**: бот не завязан на конкретный
  движок — чанк PCM уходит либо в локальный faster-whisper/Vosk, либо
  во внешний потоковый STT-сервис. Это путь масштабирования при росте
  числа одновременных звонков (однa CPU-машина упрётся в потолок):
  - **Yandex SpeechKit** (streaming) — приоритетный вариант для
    русского: низкая задержка, partial results, биллинг/комплаенс в РФ;
  - **SberDevices SaluteSpeech** / **Tinkoff VoiceKit** — отечественные
    альтернативы с тем же свойством;
  - **Google Cloud STT streaming** / **Azure Speech** / **AWS Transcribe
    streaming** — международные варианты, тоже поддерживают русский;
  - **Speechmatics / Soniox** — enterprise multi-language streaming,
    точнее, но дороже, избыточны для демо.
  - Важно: нужен именно streaming API с partial-results — например,
    **OpenAI Whisper API батчевый, не подходит** для живых субтитров.
- Partial/final текст транслируется через встроенный WS-сервер бота —
  с метаданными `room_id`/номера участников, timestamp.

## Поток данных

1. A звонит B → PBX заводит `ConfBridge`-комнату, в которой уже
   присутствует `bot`.
2. Bot получает смикшированный RTP-аудио поток разговора.
3. Аудио → PCM → STT → текст (partial/final).
4. `transcriber` рассылает транскрипт по WebSocket с `room_id`.
5. `webclient`, у которого открыт звонок в этой комнате, выводит текст
   на экран live, прямо в окне звонка.

## MVP демо на 2 абонентов

- `asterisk`: 3 PJSIP-аккаунта (1001, 1002, `bot`), одна `ConfBridge`
  комната `demo_room`, dialplan сводит туда обе стороны при звонке
  друг другу.
- `transcriber`: бот на pjsua2, автоматически регистрируется и заходит
  в `demo_room` при старте контейнера, слушает RTP, кормит в Vosk,
  шлёт текст по WS.
- `webclient`: два «профиля» (`?ext=1001` / `?ext=1002`) в двух
  вкладках/браузерах = «2 абонента», подписка на WS бота по известному
  `room_id` (для демо — комната одна, тривиально).
- TLS можно не поднимать — локальный демо на `http://localhost` /
  `ws://` браузер разрешает без TLS.

## Открытые вопросы (решить до начала кодирования)

- Транскрибировать все звонки или по фильтру (конкретные
  extension/trunk)?
- Нужна ли персистентность транскриптов (БД) — если да, это отдельная
  сущность, не обязательно в MVP.
- Какой open-source webphone взять за скелет `webclient`.
- Реальный SIP-транк оператора или только внутренняя тестовая АТС на
  старте.
- Динамическое создание конференц-комнаты на каждый звонок (для
  production, после демо).
